# AU Post Toggle Enable List

Turns the account/store-scoped toggles from a release's cards into the exact text the dev team pastes to enable them.

## Before you start

This repo's toggle-key convention has not been confirmed the way MCSL (`{accountUUID}.<flag>`) and FedEx (`{shop}.<flag>`, inconsistently) have been. Do not assume either pattern applies here. For the specific cards in scope, read the actual card description/comments the toggle came from and determine from that evidence:

- what the identifier looks like (account UUID, shop domain, something else),
- whether the card's toggle key includes that identifier as a literal prefix, or names the toggle bare with the account/store supplied separately.

Only once you've confirmed the shape from real card evidence should you generalize it for the requested identifier(s).

## Inputs

- One or more account/store identifiers (whatever form the card evidence uses — not a Trello or card id).
- A scope: a release name/guide already generated by `aupost-handoff-docs` (preferred — reuse its index table), or a Trello list/lane to read directly if no guide exists yet.

## Steps

1. **Get the toggle list per card.**
   - If a combined support guide already exists for this release (`data/handoff_docs/...md`), read its index table for the per-card toggle key(s).
   - Otherwise, pull the lane's cards via `aupost-trello-operator` and run `build_handoff_context` / `detect_toggles` from `pipeline/handoff_docs.py`, then take `ctx.toggle_names`.
   - Skip cards whose toggle is `None` / not detected.
   - `detect_toggles` in this repo has not received the markdown-bold-key hardening that MCSL and FedEx got — a toggle wrapped in `**bold**` in the card text may be missed. If a card's evidence clearly names a toggle that isn't showing up in `ctx.toggle_names`, say so rather than silently omitting it.

2. **Classify each toggle key's identifier segment**, per the card evidence you just read:
   - Template/placeholder form: replace the placeholder with the requested identifier.
   - Literal-example form: the card hardcoded a real example identifier instead of a placeholder — replace only that leading token, keep any literal suffix text unchanged.
   - Bare form: no identifier in the key string at all — do not invent one. List it separately as "not identifier-keyed; apply against the named account/store directly."

3. **Validate every given identifier before substituting.** If it's meant to be a UUID, it must be exactly 5 dash-separated hex groups of length 8-4-4-4-12. Whatever the expected shape, if what's given doesn't match, do not silently repair it — state exactly what looks wrong and still show it substituted as given, clearly flagged.

4. **Emit the result** as a fenced code block, one line per toggle, in this shape (adjust only if the card evidence's own key format differs from this):
   ```
   "<identifier>.<flag>": true,
   ```
   Group by identifier, in the order given. If multiple identifiers were requested, repeat the block per identifier with a heading naming which account/store it's for.

5. **List anything left out** — bare-form toggles, or anything you could not confidently generalize — with a one-line reason each.

## Guardrails

- Never invent a toggle not backed by actual card/comment evidence.
- Never silently repair a malformed identifier.
- This skill only produces text. There is no toggle-write API in this repo — enabling a toggle happens outside this pipeline. Do not claim or imply anything was enabled.
- If the user also wants this sent to the dev team, treat it as a Slack send under the same approval discipline as the handoff-docs skill: show content and target first, send only after explicit approval unless the destination was already named in the same request.

## Final Response

Return the fenced code block(s) exactly as specified above, plus the exclusion list from step 5 if non-empty. Do not add explanatory prose inside the code block itself — the dev team pastes it as-is.
